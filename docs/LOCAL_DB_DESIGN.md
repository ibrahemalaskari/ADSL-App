# تصميم قاعدة البيانات المحلية — التصميم والتنفيذ التاريخي

> **تحديث مهم — الإصدار 0.8.0 (25 نوفمبر 2026):** هذه الوثيقة تحتفظ بتصميم المراحل الأولى وسجل تقدمها التاريخي. بعض عبارات «لم تُربط بعد» أدناه تصف الإصدارات القديمة فقط. في 0.8.0 أصبحت مزامنة User Manager للكروت ومبيعاته مرتبطة بالجسر والواجهة ومخزنة في SQLite. مخطط القاعدة الحالي هو **3**، ويُرجى اعتماد الملحق التنفيذي في نهاية الوثيقة عند تعارض وصف قديم مع التنفيذ الحالي.

الحالة التاريخية: طبقة SQLite والترحيل وعمليات أرصدة الخطوط نُفذت في 0.7.0–0.7.4. ثم أضيف تخزين User Manager في 0.7.5، وربطته الإصدارات اللاحقة بالجسر والواجهة. في 0.8.0 أضيف نظام أرشفة مبيعات مستقل.

## 1. قواعد ملكية البيانات

| نوع البيانات | المالك/المصدر | التعديل المسموح |
|---|---|---|
| رصيد كل خط يومياً (`b`) | المستخدم؛ الرصيد لدى مزوّد الخدمة وليس في الراوتر | إدخال/تعديل من نموذج أرصدة الخطوط فقط |
| فارق التعبئة اليدوي (`o`) | المستخدم؛ مرتبط بيوم ارتفع فيه رصيد الخط بسبب التعبئة | إدخال/تعديل من نموذج أرصدة الخطوط فقط عند الحاجة |
| رصيد بداية الشهر (`op`) | المستخدم | إدخال من شاشة رصيد بداية الشهر؛ وهو أرصدة خطوط فقط |
| استهلاك الكروت في البرنامج (`p`, `lb`) | MikroTik User Manager | قراءة ومزامنة فقط؛ لا حقل تحرير يدوي |
| أعداد الكروت (`c`) | MikroTik User Manager | قراءة ومزامنة فقط؛ لا حقل تحرير يدوي |
| حالة تثبيت استهلاك اليوم (`lp`) ووقت القراءة (`lr`) وعدد المنتهية (`lx`) | منطق مزامنة User Manager | يحدّثها القارئ فقط |
| مبيعات اليوم (`s`) | مصدر المبيعات/ملف البيانات الحالي؛ ليست حقلاً يقرأه قارئ User Manager الحالي | لا تعدّل من نموذج أرصدة الخطوط؛ مصدرها المستورد يحدد في مرحلة ربط الاستيراد |
| قراءات عدادات الواجهات والفيلانات | RouterOS عند ربط القراءة | قراءة فقط |
| الإجماليات (`F`, `J`, `R`, `S`, `T`) والملخصات | يحسبها التطبيق | لا تُدخل يدوياً ولا تُخزّن كحقائق مستقلة |
| أسماء الفيلانات وحد التنبيه وربط الخطوط بالواجهات | إعدادات العرض | قابلة للتعديل في صفحات الإعدادات المخصصة فقط |

**قاعدة أساسية:** لا يوجد نموذج عام يحرّر سجل اليوم كله. حفظ رصيد خط يحدّث حقول الرصيد اليدوي وحدها. المزامنة تحدّث حقول الراوتر وحدها. لا تستبدل عملية واحدة صف اليوم بالكامل.

## 2. مخطط SQLite المستهدف

يكون ملف قاعدة البيانات داخل مساحة التطبيق الخاصة على الجهاز. يستخدم `PRAGMA foreign_keys=ON` وعمليات `BEGIN IMMEDIATE` / `COMMIT` عند ترحيل البيانات أو اعتماد قراءة راوتر كاملة.

### الجداول

- `app_meta(key PRIMARY KEY, value)` — رقم إصدار المخطط ومعلومات الترحيل.
- `lines(line_id PRIMARY KEY, label, router_interface, enabled)` — تعريف الخطوط الثلاثة وربطها الاختياري بواجهة الراوتر.
- `daily_entries(day PRIMARY KEY, created_at, updated_at)` — مفتاح اليوم `YYYY-MM-DD`.
- `line_balance_readings(day, line_id, balance_gb, updated_at, PRIMARY KEY(day,line_id))` — الرصيد اليدوي فقط؛ `balance_gb >= 0`.
- `line_balance_adjustments(day, line_id, adjustment_gb, updated_at, PRIMARY KEY(day,line_id))` — فرق تعبئة يدوي موقّع، ويمكن أن يكون سالباً.
- `month_opening_balances(month_key, line_id, balance_gb, updated_at, PRIMARY KEY(month_key,line_id))` — أرصدة بداية الشهر المقابلة لـ `S.op`.
- `daily_sales(day PRIMARY KEY, amount, source_type, imported_at)` — قيمة المبيعات ومصدرها. تُرحّل القيمة القديمة كما هي مع وسم `legacy_unknown` إلى أن يكتمل ربط مصدرها؛ ليست من قراءة User Manager.
- `router_card_days(day PRIMARY KEY, used_bytes, used_gb, is_pinned, last_read_on, expired_count, imported_at, synced_at)` — ملخص يوم الكروت من اليوزر مانجر. `imported_at` يحفظ وقت إدخال/ترحيل السجل القديم، و`synced_at` وقت آخر مزامنة حديثة.
- `router_card_counts(day, face, card_count, PRIMARY KEY(day,face))` — عدد كروت كل فئة (100، 200، 250، 500، 1000).
- `router_sync_runs(id PRIMARY KEY, attempted_at, status, read_on, date_source, summary_json, error_code)` — نتائج المزامنة دون عنوان الراوتر أو اسم الدخول أو كلمة المرور.
- `router_counter_samples(id PRIMARY KEY, sampled_at, interface_key, interface_name, interface_kind, rx_bytes, tx_bytes)` — لقطات عدادات الواجهات عند اعتماد ربطها.
- `vlan_daily_stats(day, vlan_id, metric, value, source_sample_id, PRIMARY KEY(day,vlan_id,metric))` — إحصاءات الفيلانات الفعلية بعد ربطها؛ لا تُخلط مع عينات العرض التجريبية.
- `vlan_labels(vlan_id PRIMARY KEY, label)` — أسماء العرض المخصصة للفيلانات.
- `app_settings(key PRIMARY KEY, value_json, updated_at)` — حد التنبيه وربط الخطوط والإعدادات غير السرية.
- `operation_logs(id PRIMARY KEY, occurred_at, level, code, message)` — سجل منزوع الأسرار.
- `import_batches(id PRIMARY KEY, source_type, source_name, imported_at, item_count, status)` — تتبع استيراد Excel أو مصدر آخر.

تستخدم مفاتيح الأيام والأشهر نصوص ISO (`YYYY-MM-DD`, `YYYY-MM`). تحفظ بايتات الراوتر كأعداد صحيحة 64-bit، وتحفظ الأرصدة بوحدة GB بدقة رقمية مناسبة. لا يخزّن التطبيق كلمات مرور الراوتر أو كلمات مرور الكروت أو أسماء مستخدمي User Manager.

## 3. واجهات الكتابة المسموحة

1. `saveLineBalances(day, balances, adjustments)` — يكتب `line_balance_readings` و`line_balance_adjustments` فقط.
2. `clearLineBalances(day)` — يمسح هذين الجدولين لليوم المحدد فقط، ويترك مبيعات اليوم وقراءات الراوتر كما هي.
3. `saveMonthOpeningBalances(month, balances)` — يكتب أرصدة بداية الشهر فقط.
4. `applyRouterSync(reading)` — يكتب `router_card_days` و`router_card_counts` وسجل المزامنة داخل معاملة واحدة، ولا يلمس أرصدة الخطوط أو المبيعات. عند فشل المزامنة يسجل رمزاً آمناً فقط ولا يحدّث أيام الكروت.
5. `importSales(batch)` — يستورد المبيعات مع تسجيل مصدرها، ولا يمر عبر نموذج أرصدة الخطوط.
6. `getRouterCardDay(day)` و`getAllRouterCardDays()` — قراءة بيانات User Manager مع ترتيب فئات الكروت الثابت.
7. `getLastRouterSync()` و`getRouterSyncRuns({limit})` — قراءة نتيجة آخر محاولة أو سجل محدود للمحاولات.

لا تُتاح واجهة عامة مثل `updateDailyEntry(day, allFields)` حتى لا تتمكن شاشة بالخطأ من الكتابة فوق حقول مصدر آخر.

## 4. ترحيل الحالة الحالية

| مسار `localStorage` | وجهة قاعدة البيانات |
|---|---|
| `adsl-preview-v3` → `S.d[day].b[i]` | `line_balance_readings` |
| `S.d[day].o[i]` | `line_balance_adjustments` |
| `S.d[day].s` | `daily_sales` مع `source_type='legacy_unknown'` |
| `S.d[day].p`, `lb`, `lp`, `lr`, `lx` | `router_card_days`، مع المحافظة على القيم كما هي |
| `S.d[day].c[i]` | `router_card_counts` |
| `S.op[month][i]` | `month_opening_balances` |
| `S.vn` | `vlan_labels` |
| `adsl-last-sync-v1` | `router_sync_runs` |
| `adsl-oplog-v1` | `operation_logs` بعد التحقق من تنقية السجل |
| `adsl-al` | `app_settings` |

لا تُرحّل بيانات `VD` و`VS` الثابتة في الصفحة؛ فهي عينات تجريبية وليست قياسات راوتر فعلية.

### حماية الترحيل

- إنشاء المخطط وترحيل كل البيانات في معاملة واحدة.
- فحص عدد الأيام والقيم لكل مصدر ومقارنة عينة حسابية قبل اعتماد الترحيل.
- عدم حذف مفاتيح `localStorage` القديمة في عملية الترحيل الأولى؛ تبقى قراءة مرجعية حتى اكتمال الاختبارات وموافقة المستخدم على اعتماد قاعدة البيانات.
- فشل أي تحقق يعني `ROLLBACK` وعدم اعتماد نسخة جزئية.
- النسخ الاحتياطي والاستعادة وواجهتهما مؤجلة إلى آخر مرحلة من المشروع بقرار المستخدم؛ لا تُنفّذ في هذه المهمة.

## 5. مراحل التنفيذ الخمس

1. **التصميم وحدود التحرير — مكتملة:** اعتماد ملكية الحقول ومخطط الجداول، وقصر نموذج اليوم على أرصدة الخطوط وفوارق التعبئة.
2. **طبقة قاعدة البيانات والترحيل:** إنشاء قاعدة SQLite ومستودع البيانات، وترحيل الحالة الحالية بأمان دون حذف مصدرها القديم.
3. **ربط الشاشات:** قراءة المبيعات والخطوط والأيام والفيلانات والإعدادات من المستودع، مع تطبيق صلاحيات الكتابة لكل مصدر.
4. **ربط الراوتر والسجل:** جعل المزامنة والعدادات وسجل العمليات تكتب الجداول الخاصة بها فقط.
5. **التحقق النهائي:** إغلاق التطبيق وإعادة فتحه، وفحص الاستمرارية وعدم تداخل مصادر البيانات، واختبار الترحيل والتزامن.

بعد هذه المراحل فقط تُستأنف بقية وظائف المشروع، وتبقى النسخ الاحتياطي والاستعادة آخر مرحلة كما طلب المستخدم.

## 6. التنفيذ الفعلي — الإصدار 0.7.0 (المرحلة 2، الجزء الأول)

الحالة: **طبقة SQLite الأساسية وواجهة الحالة والترحيل أُنشئت واختُبرت؛ لم يُفعّل الترحيل من واجهة التطبيق ولم تتحول الشاشات إلى القراءة/الكتابة من SQLite بعد.**

- `core/sqlite-store.js`: إنشاء المخطط باستخدام `node:sqlite` المدمج في Node.js، مع معاملات SQLite و`foreign_keys` و`WAL`.
- `bridge/server.js`: نقطتا API محليتان فقط: `GET /db/status` و`POST /db/migrate`. قاعدة البيانات الافتراضية `data/adsl.sqlite` داخل مجلد المشروع في Termux، ويمكن تغيير مسارها بمتغير `ADSL_DB_PATH`.
- الترحيل يقبل لقطة الحالة القديمة صراحةً، وينقل أرصدة الخطوط (`b`) وفوارق التعبئة (`o`) والمبيعات (`s` مع `legacy_unknown`) وحقول User Manager (`p/lb/lp/lr/lx/c`) ورصيد بداية الشهر (`op`) وآخر مزامنة والسجل والإعدادات. تحفظ `lb` بالبايت ولا يُخلط مع `p` بالجيجابايت.
- الترحيل كله داخل `BEGIN IMMEDIATE`؛ عند الفشل يحدث `ROLLBACK`. علامة `legacy_migration_v1` تمنع التكرار. لا تحذف مفاتيح `localStorage` ولا تعدّلها.
- لم تُنشأ بعد واجهات كتابة منفصلة لتحديث الأرصدة والمزامنة من الشاشات؛ لذلك لا تستخدم `/db/migrate` يدوياً ولا تحذف بيانات المتصفح. ربط الشاشات يأتي في الخطوات التالية.
- يتطلب هذا التنفيذ Node.js **22.5 أو أحدث** لدعم `node:sqlite`. هذه الوحدة ما زالت موسومة تجريبية في Node.js، ويجب اختبار توفرها على إصدار Termux الفعلي قبل اعتمادها نهائياً.
- اختبارات الإصدار: **182 ناجحة، 0 فاشلة** في بيئة التطوير. اختبارات SQLite على قاعدة مؤقتة/ذاكرة والجسر المحلي؛ لم تُختبر بعد على هاتف Termux.


## 7. واجهة مراجعة الترحيل — الإصدار 0.7.1

أضيفت في تبويب «أدوات» بطاقة تعرض حالة `/db/status` ومعاينة عدد الأيام المحفوظة في `adsl-preview-v3` وعدد قيم أرصدة الخطوط اليدوية وأيام بيانات الراوتر. لا ينفّذ التطبيق الترحيل تلقائياً؛ يلزم ضغط المستخدم على زر الترحيل ثم تأكيد نافذة المتصفح. يُرسل السجل وآخر مزامنة والإعدادات مع الحالة. إذا لم يكن مفتاح الحالة القديم موجوداً، يُرسل `{d:{},op:{}}` حتى لا تتحول عينة العرض الافتراضية إلى بيانات مستخدم. تبقى مفاتيح `localStorage` كما هي. بعد الترحيل لا تزال الشاشات تقرأ وتكتب `localStorage`؛ تحويل المستودع الأساسي وعمليات الكتابة المنفصلة مرحلة لاحقة.


## 7. مراجعة ما قبل الترحيل — 0.7.2
- تقرأ الواجهة لقطة التخزين الحالية عند الضغط، وتحسب ملخصاً للأيام والأرصدة والفروقات والمبيعات وأيام الراوتر وأعداد الكروت والأشهر وأسماء VLAN.
- الملخص محلي في المتصفح؛ الترحيل لا يبدأ إلا بعد تأكيد صريح، ثم تنفّذ طبقة SQLite المعاملة الذرية والتحقق من التواريخ.
- المصدر القديم لا يُحذف ولا يُعدّل.
- تحفظ أسماء VLAN في `app_settings(vlan_names)`.
- لا تزال طبقة القراءة والكتابة التشغيلية للواجهة غير مربوطة بـSQLite؛ هذه الجولة تعالج سلامة التحضير للترحيل فقط.

## 8. عمليات أرصدة الخطوط — الإصدار 0.7.3
- `GET /db/line-balances?day=YYYY-MM-DD`: قراءة ثلاثة أرصدة وثلاثة فروقات لليوم.
- `PUT /db/line-balances`: يستقبل `{day, balances:[...3], adjustments:[...3]}` ويحدّث صفوف `line_balance_readings` و`line_balance_adjustments` فقط. القيمة الفارغة تحذف صف الحقل المقابل.
- `DELETE /db/line-balances`: يستقبل `{day}` ويمسح صفوف الجدولين لذلك اليوم فقط.
- جميع العمليات تتحقق من التاريخ وتستخدم معاملات SQLite. لا يمكنها تعديل `daily_sales` أو `router_card_days` أو `router_card_counts`.
- واجهة اليوم تستخدم SQLite بعد الترحيل وتبقي نسخة محلية متوافقة في `localStorage`. لا تزال القراءة الأولية للتطبيق من `localStorage` في 0.7.3؛ اعتماد SQLite مصدراً وحيداً مؤجل حتى تنفيذ واستقرار مسار hydration والتحقق.

## تنفيذ قراءة أرصدة الخطوط عند بدء التشغيل (0.7.4)
أصبحت SQLite المصدر المعتمد لحقلَي الأرصدة اليدوية `b` وفوارق التعبئة `o` بعد نجاح الترحيل. يوفّر `GET /db/line-balances` قراءة جميع الأيام عند عدم تمرير `day`، أو يوماً واحداً عند تمريره. تدمج `core/line-balance-sync.js` القيم في حالة الواجهة مع استبدال `b/o` فقط والحفاظ على بقية حقول اليوم. تبقى `localStorage` نسخة توافقية ولا تُحذف. بقية الوحدات لم تنتقل بعد.


## 9. التنفيذ الفعلي — طبقة نتائج User Manager (الإصدار 0.7.5)

الحالة: **اكتملت طبقة SQLite واختبارات الوحدة؛ لم يتم ربطها بواجهة HTTP أو زر المزامنة بعد.**

- أضيفت `SQLiteStore.applyRouterSync({days, attemptedAt, status, readOn, dateSource, summary, errorCode})`.
- كل يوم يُحفظ من الحقول الموثوقة فقط: `p` و`lb` و`c` و`lp` و`lr` و`lx`. `lb` بايتات صحيحة آمنة، و`p` جيجابايت، وتُحفظ أعداد الكروت حسب الترتيب الثابت `[100, 200, 250, 500, 1000]`.
- تتحقق الطبقة من التاريخ والقيم وعدد الفئات وعدم تكرار الأيام. تحفظ اليوم وأعداد فئاته ومحاولة المزامنة في معاملة واحدة. فشل أي إدخال يؤدي إلى `ROLLBACK`.
- تُحدّث المزامنة أعمدة الراوتر فقط؛ لا تغيّر `line_balance_readings` أو`line_balance_adjustments` أو`daily_sales`. كما تحافظ على `legacy_lb` القديم المنقول ولا تكتب فوقه.
- فشل المزامنة لا يغيّر الأيام المحفوظة؛ يُسجّل وقت المحاولة والحالة ورمز خطأ آمن فقط. لا تُحفظ رسالة الخطأ الخام أو بيانات الاتصال أو أسماء مستخدمي User Manager.
- أضيفت واجهات قراءة داخل المستودع: `getRouterCardDay` و`getAllRouterCardDays` و`getLastRouterSync` و`getRouterSyncRuns`.
- رُفع `SCHEMA_VERSION` إلى 2. عند فتح قاعدة 0.7.4 القديمة يضاف العمود `synced_at` فقط، مع إبقاء الصفوف والقيم القديمة. الاختبار يغطي الترقية من مخطط 1.
- اختبارات هذا الجزء: 6 اختبارات جديدة ضمن `test/sqlite-store.test.js` تشمل الحفظ والقراءة، العزل عن الأرصدة والمبيعات، الفشل، التراجع الذري، التحقق من القيم، وترقية المخطط.
- **غير منجز في 0.7.5:** لم تُضف مسارات `/db/router-sync` بعد، ولم يتغير `www/link.js` أو زر المزامنة؛ ستنفذ واجهات الجسر في المرحلة التالية، ثم ربط زر المزامنة بها في مرحلة لاحقة.


## 9. ملحق التنفيذ الحالي — الإصدار 0.8.0

### مخطط SQLite 3

أضيفت جداول مستقلة لمبيعات User Manager، ولا تحل محل `daily_sales` أو المبيعات اليدوية القديمة:

- `sales_profile_prices(profile_name, price, updated_at)`: سعر محلي لكل باقة `actual-profile`. الأسعار لا تُستخرج آلياً من الراوتر في هذا الإصدار لأن تحليل MUMS لم يكشف نص أمر المدفوعات `Mer.asa`.
- `sales_records`: أرشيف السجلات المجمعة، بما يشمل مفتاح البيع، هوية الراوتر، اسم المستخدم، الباقة، تاريخ بدء أول جلسة، المنفذ، عدد الجلسات، حركة التنزيل والرفع، المدة والسعر المعروف إن وُجد.
- `sales_sync_runs`: سجل محاولات المزامنة ونتائجها وأعداد الجديد والمحدّث وغير المسعّر والتحذيرات.

### واجهات الجسر الحالية

- `GET /db/sales?from=YYYY-MM-DD&to=YYYY-MM-DD&profile=...&nasPortId=...&limit=...`: قراءة سجلات المبيعات والملخصات والفلاتر.
- `GET /db/sales-prices`: قراءة قاموس أسعار الباقات.
- `PUT /db/sales-prices`: حفظ الأسعار المحلية؛ لا يكتب إلى الراوتر.
- `POST /db/sales-sync`: اعتماد مجموعة السجلات المقروءة وحفظها في معاملة SQLite.

تُجرى قراءة الجلسات ثم المستخدمين بالتتابع، لأن عميل API الحالي لا يربط ردود الطلبات المتوازية بمعرفات مستقلة. القراءة للقراءة فقط. لا تُطلب كلمات مرور البطاقات أو عناوين IP/MAC أو caller-id أو التعليقات. مسارات مبيعات الإصدار الحالي مخصصة لـRouterOS v6؛ RouterOS v7 يُرفض بوضوح بدلاً من تمرير مسار غير متوافق.

### قواعد التجميع والتحفظات

- تُزال الجلسات المكررة بواسطة `.id` ثم تُجمع الجلسات حسب اسم المستخدم؛ تُجمع حركة التنزيل والرفع والمدة، وتُربط الباقة من `actual-profile`.
- الحقل المفقود لا يتحول إلى قيمة مالية افتراضية. حركة الرفع/التنزيل الناقصة تعرض بتحذير وتُحسب صفراً مؤقتاً لذلك الحقل؛ السعر الذي لا يملك تعييناً يبقى `NULL` ولا يُحتسب إيراداً معروفاً.
- التاريخ المعروض هو تاريخ أقدم `from-time` معروف، وليس إثباتاً لوقت الدفع النقدي. ويفترض التجميع أن اسم المستخدم بطاقة واحدة لا يعاد استخدامها لعملية بيع أخرى.
- مفتاح منع التكرار يعتمد هوية الراوتر واسم المستخدم وأول معرّف جلسة/وقت متاح. تغيير هوية الراوتر أو حذف أقدم جلسة قد ينتج مفتاحاً مختلفاً؛ يجب فحصه في اختبار القبول قبل اعتماد تقارير مالية نهائية.
- قائمة التفاصيل وملف CSV محدودان بـ5000 سجل للفترة المعروضة؛ ملخصات SQL اليومية وإجمالياتها تحتسب كامل الصفوف المطابقة.

### الحالة والاختبارات

تتضمن الحزمة 0.8.0 اختبارات parsers والتجميع وإزالة التكرار والتسعير وقراءة RouterOS الوهمية ومعاملات SQLite ومسارات الجسر. آخر تشغيل كامل سجّل **211 اختباراً ناجحاً و0 فاشل** على Node.js 22.16.0. هذا لا يثبت بعد توافق كل حقول MUMS مع الراوتر الفعلي، ولا يمثل اختبار قبول على هاتف Termux؛ تُراجع خطة القبول في `docs/SALES_MODULE.md`.
